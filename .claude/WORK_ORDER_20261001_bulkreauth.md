# WO 20261001-bulkreauth — 핀 일괄삭제: 소유자 노출 + 본인 재인증(구글 재로그인)
Jev route: (발주 직전 지휘자 실행·기입)

## 마스터 원문
"핀 일괄삭제 기능도 구현해. 이때는 구글 비번을 넣게 해"

## 사실 (지휘자 확인)
- 일괄삭제는 이미 있다(8da7ed3): 11_UI 트리 핀 목록 [선택] → [선택 삭제 N개], 구역 노드 [이 구역 (모드) 핀 전체 삭제]. 노출 조건은 `Auth.isAdmin`(super/admin, 22_Auth.js:29)이다. 마스터는 공용 자동입장 계정(designer)으로 써 왔기 때문에 **화면에 보이지 않았다**(라이브: 디자이너 계정 버튼 숨김 확인, RESUME_LEDGER 103a60fc).
- 🔴 "구글 비번 입력" 해석: 앱이 구글 비밀번호를 직접 입력받는 폼은 **금지**한다(피싱 구조, 구글 정책상 앱이 검증할 수 없음). → **Firebase 재인증**으로 구현한다: `reauthenticateWithPopup(GoogleAuthProvider)`. 사용자는 구글의 공식 창에서 비밀번호나 2FA를 입력한다. 로컬 세션 계정(`local-`, 회사 이메일 가입)은 앱 비밀번호 재입력으로 대체한다(서버 검증).

## 판정 기준
1. 노출: 프로젝트 **소유자 + super 관리자**에게 일괄삭제 UI를 보인다(보안 팀이 확정한 "초대·제거는 소유자·super만"과 같은 권한 판정 SoT를 재사용한다. 없으면 그 팀 커밋 이후 생긴 헬퍼를 쓴다). 일반 멤버와 열람자에게는 숨긴다.
2. 재인증: [선택 삭제]나 [구역 전체 삭제] → 개수 확인(Prompt.confirm) → **재인증 창**(Google 계정이면 구글 공식 팝업, 로컬 계정이면 앱 비밀번호 입력 모달) → 성공해야 삭제를 실행한다. 실패나 취소면 삭제 0건이다. 재인증은 **5분 동안 유효**(이름 있는 상수)해서, 연속 삭제 시 매번 묻지 않는다.
3. 서버 측 확인: 클라이언트는 재인증 직후 받은 **새 ID 토큰**(Firebase `auth_time` 클레임) 또는 로컬 재인증 성공 시 서버가 발급한 단기 토큰(5분)을 일괄삭제 PATCH 요청 헤더(예: `X-Reauth`)에 싣는다. 서버는 `auth_time`이 5분 이내인지, 또는 단기 토큰이 유효한지 확인한다. 이 헤더가 있는 요청에서 재인증이 무효하면 403. 한계: pins JSON 통째 저장 구조라 헤더를 빼고 보내는 요청은 서버가 일괄삭제로 식별할 수 없다. 이 한계를 보고서에 정직하게 적는다(UI 오조작·무단 사용 방지 목적).
4. 모바일: 팝업이 막히는 환경이면 `reauthenticateWithRedirect`로 폴백한다.
5. 기존 삭제 경로(`_removePins`, tombstone, LWW)를 그대로 쓴다. 새 삭제 로직은 금지.

## 검증
- 회귀 테스트:
  - 소유자·super에는 보이고 멤버·열람자에는 숨김
  - 재인증 성공 → 삭제
  - 재인증 실패·취소 → 0건
  - 5분 이내 재사용, 5분 경과 시 다시 요청
  - 서버 `X-Reauth` 만료 → 403
  - 각 항목 뮤테이션 EXIT=1
  - Firebase 호출은 테스트 하니스에서만 가로챈다(실제 구글 창은 지휘자가 배포 후 실측 불가 → 마스터 확인 항목)
- 전 스위트는 HEAD 추출본 fail 0.
